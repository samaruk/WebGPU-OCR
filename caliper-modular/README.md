# CALIPER

**Browser-only, WebGPU-accelerated invoice layout analysis.**

CALIPER takes a photographed or scanned invoice and, entirely in the browser with no server and no external libraries, finds its printed rules, its text lines and the row × column structure of the item table. Every intermediate stage is rendered to a clickable gallery so each parameter can be tuned against what it actually changes.

## Requirements

- A browser with **WebGPU**: recent Chrome or Edge, or Safari Technology Preview. The pipeline does not run without it.
- A static file server. The app uses ES modules, so it cannot be opened directly from `file://`.


The optional OCR service needs the .NET 8 SDK (or newer) and restores its packages from nuget.org on first build; the PaddleOCR models are bundled in the packages, so that engine runs offline afterwards. Tesseract 5 joins in when `tesseract.exe` is installed (the UB-Mannheim build on Windows, `apt install tesseract-ocr` elsewhere), EasyOCR when the Python interpreter named by `Ocr:EasyOcr:Python` has it (`pip install easyocr`; PyTorch comes with it and the models download on the first start). Neither is required: a missing engine reports its status and the others carry on.
## Running

Serve the folder and open `index.html`:

```bash
npx serve .
```

or

```bash
python -m http.server 8080
```

Then drop a PNG, JPG, WEBP or BMP onto the drop zone and click **RUN PIPELINE**. Images larger than the GPU storage-buffer budget are downscaled on load and the new size is shown in the metadata panel.

## Pipeline

The pipeline has nine steps and 28 gallery stages. Sidebar sections are numbered to match.

### 00 · Watermark removal — stage 2

Remove watermark ([js/watermark/watermark.js](js/watermark/watermark.js)) returns a large low-contrast watermark (a logo, a PAID stamp) to the paper tone and shows the result; RUN PIPELINE then starts from the cleaned image, and Restore original swaps back. The paper tone at every pixel is the local maximum of the luminance over a window wider than a text line, taken at 1/8 scale, max-filtered, blurred and upsampled, so inside a watermark the tone is the watermark's own grey. A pixel's contrast against that tone decides it: at or below the watermark contrast (section 00 slider, default 0.15) it is lifted to the paper tone with its hue kept, at 1.8 times that or more it is ink and stays, between it is blended. Text printed over the watermark keeps its contrast against the grey and survives.

### 00b · Rectification

The **Rectify image** checkbox, on by default, runs two geometric corrections: a self-calibrated radial lens correction ([js/lens/lens.js](js/lens/lens.js)) and a perspective rectification that finds the page quad and warps it back to a rectangle ([js/rectify/rectify.js](js/rectify/rectify.js)). When it is off, every stage works on the original image. Stages 1 to 3 show the source, the lens-corrected and the rectified image.

### 00c · OCR API: PaddleOCR + Tesseract 5 + EasyOCR — stages 5 to 8

Independent readings of the page by three more engines. The rectified image is POSTed as multipart `file` to the .NET service in [api/InvoiceOcrApi](api/InvoiceOcrApi) (`POST /api/invoice/analyze?depth=brief|deep|both`, default both) the moment it exists, and the pipeline carries on without waiting ([js/api/api.js](js/api/api.js)). The service runs three engines on the same pixels at once: PaddleOCR PP-OCRv5 in process (Sdcb.PaddleOCR, CPU, models bundled), Tesseract 5 through the installed `tesseract.exe` (found on the PATH or in the usual install folder, or named by `Ocr:Tesseract:Exe`; hOCR mode with character boxes, so every word comes back with its box and confidence and every character inside it with its own box and confidence), and EasyOCR through a Python worker (`easyocr_worker.py`, started once; needs `pip install easyocr`, the models download on the first start). An engine that is not installed, still loading or failing reports its status under `engines` and the rest of the answer is unaffected. Every engine's reading is returned as characters (`engines[].characters`: one symbol each with text, confidence 0–1, box, the index of the word or region it belongs to, and `estimated`): Tesseract's boxes are the engine's own, PaddleOCR's and EasyOCR's are interpolated along the region by character count and flagged estimated; the browser rebuilds words by grouping the symbols on their word index. PaddleOCR's regions give the layout; the other engines' words are placed into the same rows and columns (`deep.table.engineCells`) and voted cell by cell (`deep.table.consensus`, with `consensusSource` naming who supplied each cell: a text two engines agree on, else the most confident reading, PaddleOCR first on a tie; in a numeric column only clean numbers vote). The answer fills four API stages whenever it arrives, whether the pipeline is still running or long done: one stage per engine with that engine's own regions (PaddleOCR's regions, Tesseract 5's words, EasyOCR's fragments), each box with its text coloured by confidence and a badge with the count, mean confidence and server time, or the engine's status when it did not run; and the combined stage: outside the item table PaddleOCR's regions in grey, inside it every cell character by character — the engine that supplied the cell's voted text is the anchor, each of its symbols is drawn in its own box and coloured by which engines read the same symbol at the same place (white all three, yellow PaddleOCR + Tesseract, cyan PaddleOCR + EasyOCR, green Tesseract + EasyOCR, a symbol only one engine read in that engine's colour: orange PaddleOCR, violet EasyOCR, pink Tesseract), so a label two engines spell differently shows exactly which characters they dispute; a pink outline marks a symbol box the engine reported itself; a legend with character counts along the bottom of the image, the service's header / item table / footer split with its columns, and in the badge each engine's status, word count and time. The layout mirrors the column stage at region level: rows on a de-skewed centre y, the longest run of rows with three or more regions as the table, columns from a coverage profile of the region boxes along the column slope, the footer cut at a totals row (keywords or an empty first column) unless a run of item rows follows, and key fields (invoice number, dates, totals, amount in words) by regex over each row. Start it with `dotnet run` in `api/InvoiceOcrApi` (listens on http://localhost:5080; CORS open); the endpoint and depth are set in section 00c.

### 01 · Binarisation

Sauvola adaptive thresholding on the GPU ([js/webgpu/webgpu.js](js/webgpu/webgpu.js)), plus the connectivity and minimum component area used by every later analysis.

### 02 · Borders · rules — stages 9 to 14

The rule detector ([js/borders/borders.js](js/borders/borders.js)) traces solid and dashed rules on a separate Sauvola binary built with a lower threshold weight. The layout module ([js/borderlayout/borderlayout.js](js/borderlayout/borderlayout.js)) interprets them: intersecting rules form grids, and the grid with the most rule crossings is the printed structure (a pen line down the page edge meeting a signature underline spans a huge box on two crossings and loses to a boxed title row crossed by its separators dozens of times); three or more horizontals with verticals give the whole table from borders, two horizontals with verticals give the region and columns, a short boxed header row gives column boundaries extended down to a totals line of the same width, stacked long horizontals bound an open table (two of them, header underline and totals line, give the region; four or more at a regular pitch that belong to no grid, a rule under every item row, give the row bands outright and outrank a boxed customer block that would otherwise pose as a vertical grid), and long rules outside the table are section separators. Every rule is then painted out of the working image with the surrounding paper, following the actual ink run of each rule so the soft fringe of a photographed rule goes too. All later stages process this rule-free image.

### 03 · Text lines · clean — stages 15 to 19

The text-line module ([js/textlines/textlines.js](js/textlines/textlines.js)) turns character components into clean text lines. The reference glyph height is an ink-weighted median that ignores solid components, so halftone cannot drag it down. The component filter ([js/heightfilter/heightfilter.js](js/heightfilter/heightfilter.js)) cuts tall components at their ink valleys and drops anything too short, still multi-line or rule-shaped. Survivors are chained by horizontal proximity, vertical overlap and comparable height. A component whose neighbours sit on two different lines is a bridge, a pen tick or stroke reaching across, and can never join them. A Theil–Sen line through each chain splits two-line merges and drops off-line marks. Lone components must look like a glyph and sit inside the page. Accepted chains are joined left to right into full lines ([js/lines/lines.js](js/lines/lines.js)) in a de-skewed frame, each piece against its nearest neighbour, one piece per x position, never taller than one line, and drawn as a polygon that follows the pieces. Only the ink of accepted lines survives into the clean binary.

### 04 · Columns — stages 20 to 24

The column module ([js/columns/columns.js](js/columns/columns.js)) reads the table skeleton from the full lines in the de-skewed frame. Rows and columns get separate slopes: the rows' slope de-skews y, while x is de-skewed along the columns, whose slope is the one under which the table rows show the most clear bins in their coverage profile (searched ±3.4° around the rows' slope). On a rectified photo the two differ by a residual shear, and de-skewing x with the rows' slope would shear every column and fill the narrow gaps between TP and VAT. Rows with enough pieces form runs; the run with the most column structure seeds the band, or a table box from the border stage does. Foreign rows that cross a third or more of the gutters are trimmed off the ends, the band grows through every adjacent column-compatible table row, and other runs across damaged rows are merged in when they share the columns, so one invoice yields one whole item table. A glyph coverage profile across the band exposes the gutters, either as clear runs almost no row crosses or as deep valleys at most 42 percent of the neighbouring peaks, which finds columns separated only by a word space. A valley too narrow for a gutter (0.4 glyph heights for a clear one, 0.6 for a deep one, so a single character gap or a word space never qualifies) is skipped in favour of the next valley of the same stretch. Border column boundaries are added where the coverage allows. Every invoice is header, item table and footer. Inside the band, a tabular row that does not respect the gutters and has under 60 % of the pieces of a table row is foreign (a Client Name / Bill No. block glued to the table), and the table is the block between such rows holding the most tabular rows; an item row whose name ran into the next column keeps its piece count and never breaks a block, nor do non-tabular rows, so a table damaged by a fold or watermark stays whole. Then: thin rows are first folded into the item row they sit on (a product code that drifted into a row of its own), two band rows that share no x range while their vertical extents overlap by a third are the two halves of one physical row a curled page split and are merged, then, once the item rows are established, the first tabular row whose first column (code / serial) is empty, that fills clearly fewer columns than an item row and that is followed by fewer first-column rows than precede it, is a totals row and the table ends before it, and after recognition the rows reading Sub Total, Grand Total, Amount in words or Free Product are handed back to the column stage, which ends the table before the first of them. Either way, a totals row followed by item rows (three of the next six tabular rows carry a first-column entry) is a sub-total inside the table (one page can carry several product groups) and does not end it. Columns are classified left, right or centre aligned, and every glyph goes to the column under its centre to form the cell grid.

After recognition the title words are matched against the header rules in [js/config/headerrules.js](js/config/headerrules.js) ([js/headerrule/headerrule.js](js/headerrule/headerrule.js)): one rule per known template, each column with a semantic key, its printed label and its left / right edge as a fraction of the header width. The label tokens of every rule are aligned to the title words in order (fuzzy, skips allowed); the rule with the most columns found wins when at least four and 70 % are found. A first alignment gives rough title positions; a second pass matches each column's label inside its mapped x-range, which a two-line title cannot fool (the second line sits a little left and would otherwise hand its word to the next column). The map from rule fractions to page x is a Theil–Sen fit through the found titles, and boundaries are placed left to right: each goes to the nearest unused detected gutter between the two neighbouring titles within half the two columns' width (a deep-but-not-clear valley pays a penalty, so the clear gutter beside it wins), else to the mapped position, never stepping back. A rule drives the columns only when it matches exactly: every title found, in the rule's order, and its boundaries on the page's own gutters when the profile shows as many. Otherwise the columns found from the coverage profile stand and are only named: the title words above each column are matched against the vocabulary of every rule's labels, and the column takes the key of the label it carries (Batch, Qty, VAT … wherever those words are printed), with unlabelled columns left unnamed. A page whose titles come in another order, Qty before Pack Size, is a different layout; add it as a rule to have its columns driven exactly. The rule's columns then replace the profile's, with their keys, and the cells and cell texts follow. A page that matches no rule keeps the columns found from the profile. Add a template by copying a rule in that file.

### 05 · Characters — stages 25 to 27

The character module ([js/characters/characters.js](js/characters/characters.js)) makes every box one symbol. Inside each accepted line, components whose x ranges overlap are stacked parts of one symbol and are joined, such as the dot and stem of an i. A symbol much wider than the line's median character width is a merge and is cut at the significant valleys of its column ink profile, with slivers merged back. Each character records its line, its member components, how it was made and the table cell it lies in. The stages show the character boxes, the split profiles with cut positions, and a contact sheet of every character crop.

### 06 · Recognition — stages 28 to 30

The recognition module ([js/recognition/recognition.js](js/recognition/recognition.js)) loads Tesseract.js from the jsDelivr CDN on first use and recognises every full line in single-line mode with the dictionaries off, so batch codes and amounts are not "corrected" into words. Each row crop holds only the row's own glyphs, sheared level with the page tilt and upscaled so the glyph height lands on the target (40 px). The crop is the page's own grey inside the glyphs' outline grown by 3 px, levels normalised from the row itself, so the engine sees the real anti-aliased strokes rather than a threshold mask (the default; section 06 can choose the binary mask instead, robust on a heavy watermark, or the better of both, which reads the binary crop too whenever the grayscale reading is unsure). Punctuation is drawn slightly fatter in the binary crop so decimal points survive the engine's noise filter. Once the columns are named, a second pass reads the numeric columns with a digits-only character whitelist, and the batch, pack, unit, code and type columns with letters and digits only: all the cells of a column are stacked into one image with a clear gap between them and read in a single call, each result line going back to its cell by position, so the pass costs one engine call per column rather than one per cell. A cell reading at least as confident as the line's replaces it, so an 8 no longer turns into a B or a 1 into an I inside a number. The character boxes are then reconciled with the engine word by word: when a word has as many boxes as characters they map one to one, otherwise the word's region is re-segmented into exactly that many boxes at the best ink valleys, so every character carries a text and a confidence. Chains sitting on a dark background, the desk around the paper, are rejected as off-page before any of this. The text of each table cell is assembled from the characters inside it. The stages show the recognised symbol over every box coloured by confidence, the text of each full line, and the recognised text of each table cell. The first run needs a network connection to fetch the library and language data; later runs use the browser cache.

### FINAL · best analysis — stages 31 and 32

When both readings are in ([js/final/final.js](js/final/final.js)), the final table is rebuilt from both. Header: one title row whose labels are the matched header rule's, else the API's title words, else the local ones; local band rows above the title (a key-value block glued to the table) are dropped. Rows: where the API found a table, its item rows below the title come first, since PaddleOCR reads a curled row as one row where the local join splits or swallows it; every local band row is attached to the API row holding its centre, and local rows no API row covers are rows of their own. An API row must fill columns like an item row, else it is one of the API's own key-value rows. Leading and trailing rows that fill hardly any column (a section title, a reference number) go, two neighbouring rows whose filled columns do not overlap and together make an item row are joined, and rows without any text go. Columns: the local structure, keyed by the rule when one matched, with every API region split into words and each word assigned to the column under its centre; a word whose box straddles a column boundary (VIALC0321007, T30610121) is cut at the character under the boundary, counted from the local character boxes. A weak API reading (confidence under 60) yields to a local one at least as confident. Text per cell by a vote among the four readings, PaddleOCR, EasyOCR, Tesseract 5 and the local Tesseract.js one: a text at least two of them agree on (same letters and digits, spaces and punctuation aside) wins, the largest group first, then the group holding PaddleOCR, then the more confident, spelled the way the engine highest in that order spelled it and, in a numeric column, the way that gives one clean number, so Tesseract 5's 26240 confirms PaddleOCR's 262.40 and the decimal point stays. When no two readings agree, PaddleOCR first: its text when the local reading agrees or it is confident (85 or more); the local reading where PaddleOCR has none, in a numeric column only a well-formed number (a pen tick makes Tesseract read 7 1 or 17°); and where PaddleOCR is unsure, the local reading only if it is clearly more confident (by 10) and no less plausible, well-formed in a numeric column when PaddleOCR's is, elsewhere with a character shape at least as common in that column; without a PaddleOCR reading the most confident other engine stands in for it. The Compare stage shows the local and PaddleOCR readings per cell with disagreements outlined red; the Final Table stage draws a bordered table, header row and full cells, with the chosen text coloured by its source (white agreed, yellow settled by vote, orange PaddleOCR, violet EasyOCR, pink Tesseract 5, green local) and a badge counting the cells each source supplied and the rows each side contributed. The same table is shown as JSON in section 07 (Final table · JSON, with a Copy button) and in the layout export under finalTable: the engines that took part, header labels and keys, one object per row with the cell texts by key, the source of every cell (vote:paddle+tesseract5, agreed, api, local, …) and every engine's reading of it. Without a local table the API table stands as it is; while the API answer is pending or failed the local reading stands with a note, and the stages redraw on their own when the answer lands.

### FINAL · number check

The number columns of an item row are one computation printed several times, and the check module ([js/numcheck/numcheck.js](js/numcheck/numcheck.js)) uses that to validate and repair the final table's cells. It runs on the final table JSON and its result is added to it as `numberCheck` (the roles, the relations in force, a summary) and per row as `check` (a status per number cell) and `corrected` (the text a filled or fixed cell should carry). Columns are first mapped onto roles: quantity, bonus, unit TP, unit VAT, VAT %, unit TP+VAT, unit SP, total TP, total VAT, total SP, discount %, discount amount, unit discount, net. A rule key names its role directly; an unnamed column is read from its title words (Qty, Bonus, TP, VAT, Total, Value, Disc, %, Net …) and from its numbers (values written with % are a percentage). The rules are written over the roles, as relation variants: unit TP+VAT = unit TP + unit VAT; unit VAT = unit TP × VAT %; total TP = qty × unit TP; total VAT = qty × unit VAT, or total TP × VAT %; discount = total TP × discount %, or (total TP + total VAT) × discount %, or qty × unit discount; net = total TP + total VAT − discount, or qty × unit TP+VAT − discount, or total TP − discount, or total SP − discount. Which variant a template follows is not assumed: a column printed as VAT may be the unit VAT, the VAT % or the total VAT, a discount column an amount, a percentage or a per-unit amount, so every reading of the ambiguous columns is tried and the one under which the most complete rows add up wins, and among the variants of one target only the one the rows satisfy stays in the model. A table that prints unit TP and unit VAT without a VAT % gets its VAT ratio from the rows themselves when they agree on one (17.4 % on invoices that compute VAT on the MRP), and zero-VAT rows are exempt items, not errors. Then row by row: a relation with exactly one value missing fills it (a blank cell, or a reading that is not a number); a violated relation names the value to change, and the change that satisfies the most relations and breaks none is applied when the corrected number is a plausible misread of the printed text (one digit off, a dropped or extra digit, a shifted decimal point, or what another engine read in that cell), or when two independent relations agree on it; a sub-total row (Sub Total, Total, or a row whose numbers are the column sums) checks the sums and settles a lone doubtful cell by the difference. Tolerances follow the printed rounding: two decimals per term, per-unit rounding scaled by the quantity. Every number cell ends as verified, filled, fixed, conflict (a violated relation the check could not settle), unverified (its relations could not be evaluated), unchecked (no relation reaches its role, such as bonus) or blank. A column no rule or title names is left alone, and a table whose columns form no relation is reported as such.

## Stage gallery

Every stage is rendered at full resolution into the gallery under the viewport; click any panel to inspect it with pan and zoom. The list lives in [js/config/config.js](js/config/config.js). The border stages show the binary, both openings, the rules, the erased image and the interpreted layout. The text-line stages show the binary, the component filter, the chains with rejection reasons, the full lines and the clean binary. The column stages show the row bands, the coverage profile with gutters, the columns, the cells and the table layout.

## Exports

- **Stage PNG** downloads the currently displayed stage at full resolution.
- **Layout JSON** downloads `caliper_layout.json` with the parameters, the border layout, the text lines and full lines with polygons and centrelines, the table band, gutters, columns with alignment and cells, every character with its box, kind, cell, text and confidence, and the recognised line and cell texts.

## Project layout

```
index.html              controls, viewport and gallery markup
css/caliper.css         styling
js/main.js              entry point: imports every module, initialises the GPU
js/config/              ordered stage list
js/state/               the shared mutable state object S
js/dom/                 DOM handles resolved once
js/webgpu/              WGSL compute shaders: Sauvola, dilation, erosion, opening
js/cca/                 union-find connected components
js/morph/               CPU dilation, smoothing and medians
js/hull/                convex hull (used by the page-quad fit)
js/lens/                radial lens-distortion correction
js/rectify/             page-quad detection and perspective rectification
js/borders/             rule tracing, solid and dashed
js/borderlayout/        rules → grid, header box, row rules, sections; erase mask and inpainting
js/heightfilter/        component height filter with multi-line splitting
js/lines/               full-line join, de-skewed, polygon outlines
js/api/                 OCR web API request (fire and forget) and the engines of its answer
js/final/               best of the local analysis and the API answer
js/numcheck/            arithmetic check of the number columns: roles, relations, fill and fix (node numcheck.test.mjs)
api/InvoiceOcrApi/      .NET 8 web API: PaddleOCR (Sdcb.PaddleOCR) + Tesseract 5 (tesseract.exe) + EasyOCR (Python worker), region-level layout, per-cell vote
js/textlines/           glyph chaining → text lines → clean binary
js/columns/             table band, gutters, columns, cells
js/characters/          one symbol per box: join stacked parts, cut merged symbols
js/recognition/         Tesseract.js per full line, symbols mapped onto the character boxes
js/pipeline/            the conductor: readParams and runPipeline
js/render/              one drawing routine per stage kind
js/gallery/             stage thumbnails
js/viewport/            pan and zoom blitter
js/imageload/           file decode with GPU-budget downscaling
js/ui/                  slider bindings and export buttons
```

Each module starts with a comment explaining why it exists and how it works. The shared state object is exported as `S` from [js/state/state.js](js/state/state.js) and can be inspected from the browser console after a run.
